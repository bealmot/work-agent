# Zendesk via its own API

Zendesk's accessibility tree is ~74 KB / 15,000+ elements and truncates before
it can be parsed. The same facts are a few hundred bytes of JSON from an
endpoint this browser is already authenticated to. **Prefer the API for every
read.** Where it works, reads need no navigation at all.

Verified on this machine **2026-08-06: 10/10 calls succeeded.** The session
cookie authenticates same-origin GETs; no token, no admin approval, no CDP.

## Prerequisites

If a call reports either of these missing, that is an **unset prerequisite, not
a capability limit**. Set it and retry; never record the API as unavailable.

- Chrome → Develop → *Allow JavaScript from Apple Events*
- `CUA_DRIVER_ENABLE_LEGACY_PAGE_MUTATIONS=1` on the cua-driver daemon

## The call shape

**Refresh `window_id` via `list_windows` immediately before every call.** A
stale one crashes the MCP server outright — not an error you can catch, and
there is no session left to retry in. Keep the `pid` stable; only the window
identifier churns. See browser-ops.

    page:
      action: execute_javascript
      window_id: <fresh, from list_windows just now>
      target_url_contains: "<host>/agent"
      javascript: <one expression returning a string>

- **Pin to `<host>/agent`**, never the bare word `zendesk`. Loosely pinned, the
  call lands in one of Zendesk's hidden `about:blank` iframes and returns empty
  with no error. Read the host from `local/sites.yaml`.
- **Relative paths only.** `fetch('/api/v2/…')` inherits the tab's origin, so
  the session cookie rides along. An absolute URL is cross-origin and dies.
- **Self-identify every read:** `JSON.stringify({url: location.href, data: …})`.
  If `url` is not the agent tab, the result is void however plausible it looks.

### Pick an await form once, then reuse it

A SyntaxError about `await` reads exactly like a blocked fetch. Try both before
concluding anything:

    A  JSON.stringify({url:location.href, data: await (await fetch(U)).json()}).slice(0,300)
    B  fetch(U).then(r=>r.json()).then(d=>JSON.stringify({url:location.href,data:d}).slice(0,300))

If B returns `[object Promise]` or `{}` instead of data, the executor is not
awaiting at all. That is a third failure mode, and it is still not a blocked API.

## Response size — you are the only limit

**The shim does not clamp this.** It bounds `get_window_state` /
`get_browser_state` only; a `page` result passes through whole. Your `.slice()`
is the entire backstop, and context is append-only — an oversized response is
permanent for the session.

1. **Project inside the page.** `.map` to the fields you need. A raw ticket
   object is dozens of fields of custom data, tags, and `via` metadata.
2. **`.slice(0, N)` every call.** 300 for a probe, ~1500 for a list. If a slice
   truncates, project harder — do not raise N.
3. **Never sideload.** `?include=users,groups` multiplies the payload. Fetch the
   one user by id instead.

## Endpoints

All relative, all GET, all `.json`.

| Endpoint | Project to |
|---|---|
| `users/me.json` | `{id, role}` — channel + auth proof |
| `views.json?per_page=100` | `{id,title}` — once per session |
| `views/{id}/tickets.json?per_page=25` | `{id,status,subject}` |
| `tickets/{id}.json` | `{id,status,priority,subject,requester_id,tags,updated_at}` |
| `tickets/{id}/comments.json` | count first, then `slice(-3)` |
| `search.json?query=…` | when you have no id |
| `users/{id}.json` | resolve one `requester_id` to a name |

    d.comments.slice(-3).map(c=>({id:c.id, public:c.public,
      author:c.author_id, body:(c.plain_body||'').slice(0,800)}))

- **`plain_body`**, not `body` or `html_body`.
- **`public:false` marks internal notes** — prior troubleshooting lives there.
  Keep the flag in every comment projection.
- `per_page` caps at 100.
- **View order is not screen order.** If the human has sorted or filtered the
  UI, the top rows differ. Say which order you used.
- **`429` → back off and obey `Retry-After`.** The quota is shared with the
  human working alongside you. It does not mean try another channel.

## Where the API stops

- **Zendesk Explore** — no public API. GUI only.
- **Unsaved UI state** — what is typed in a composer, an open macro preview.
- **Attachments** are binary. Report `file_name`, `size`, `content_url`; never
  pull the bytes into context.
- **Anything a human is meant to look at** — navigate and let them see it.

## Composing with navigation

Ids from JSON → content from JSON. For a read-only question you are done, with
no navigation at all.

Navigate only to show a human something or to draft a reply: set the address bar
to `https://<host>/agent/tickets/{id}` and press Enter. Read the address bar's
element index fresh each time (browser-ops). This skips the ticket list
entirely, so neither AX index drift nor pixel drift applies.

## Writes — GET only

A CSRF token is available (`authenticity_token` from `users/me.json`) and write
endpoints exist. **Do not use them.** The standing rule is draft, never send:
compose replies and leave them for human review. Status changes, comments,
macros and assignments all require explicit per-action human approval, whatever
the mechanism.

## When a read comes back empty

An empty result is a channel failure until proven otherwise. Prove it with
something that cannot legitimately be empty:

    JSON.stringify({url:location.href, title:document.title,
                    ready:document.readyState, ok:1+1})

- nothing returned → JS execution is blocked; check the prerequisites above
- `url` is `about:blank` or not the agent tab → wrong target; pin it properly
- `ok:2` but the fetch is empty → *then* investigate the endpoint

Never build a theory on an empty result.
