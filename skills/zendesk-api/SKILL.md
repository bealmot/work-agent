# Zendesk via its own API

Zendesk's accessibility tree is ~74 KB / 15,000+ elements and truncates before
it can be parsed. The same facts are a few hundred bytes of JSON from an
endpoint this browser is already authenticated to. **Prefer the API for every
read.** Where it works, reads need no navigation at all.

Verified on this machine **2026-08-06: 10/10 calls passed.** The session cookie
authenticates same-origin GETs; no token, no admin approval, no CDP.

**Measured: ~500 bytes of JSON against ~59 KB of accessibility tree for the
same ticket list — roughly 100x.** And the JSON carries stable ticket ids, so
none of the AX index drift applies.

## Prerequisites

If a call reports either of these missing, that is an **unset prerequisite, not
a capability limit**. Set it and retry; never record the API as unavailable.

- Chrome → Develop → *Allow JavaScript from Apple Events*
- `CUA_DRIVER_ENABLE_LEGACY_PAGE_MUTATIONS=1` on the cua-driver daemon

## The call shape

**Refresh `window_id` via `list_windows` immediately before every call.** A
stale one crashes the MCP server outright — not an error you can catch, and
there is no session left to retry in. Keep the `pid` stable; only the window
identifier churns. See browser-ops.

    page:
      action: execute_javascript
      window_id: <fresh, from list_windows just now>
      javascript: <a synchronous IIFE returning a string>

### `fetch` does not work here. Use synchronous XHR.

**`execute_javascript` returns only synchronous results — a promise returns
empty.** Both `await` and `.then()` chaining fail, and they fail *quietly*,
returning `{}` or `[object Promise]`, which reads exactly like a blocked API.
Verified 2026-08-06.

The working pattern is synchronous `XMLHttpRequest` inside an IIFE:

    (function(){
      var x = new XMLHttpRequest();
      x.open('GET', '/api/v2/users/me.json', false);   // false = synchronous
      x.send(null);
      var d = JSON.parse(x.responseText);
      return JSON.stringify({url: location.href, id: d.user.id, role: d.user.role});
    })()

Every example below uses this shape. If you find yourself writing `fetch`,
`await`, or `.then()`, you are writing a call that returns nothing.

### Do NOT pass `target_url_contains`

It triggers CDP discovery, which fails on this Chrome configuration —
`--remote-debugging-port` is refused on the managed profile. Passing it breaks
the call. Verified 2026-08-06.

**Targeting is the `window_id`**, taken fresh from `list_windows` immediately
before the call. Which makes the self-identifying read essential rather than
merely good practice:

- **Always return `url: location.href`** in the result. It is now your *only*
  confirmation that the JS ran in the tab you meant. Zendesk keeps hidden
  `about:blank` iframes; if `url` is not the agent tab, the result is void
  however plausible it looks.
- **Relative paths only.** `/api/v2/…` inherits the tab's origin, so the session
  cookie rides along. An absolute URL is cross-origin and dies.

## Response size — you are the only limit

**The shim does not clamp this.** It bounds `get_window_state` /
`get_browser_state` only; a `page` result passes through whole. Your `.slice()`
is the entire backstop, and context is append-only — an oversized response is
permanent for the session.

1. **Project inside the page.** `.map` to the fields you need. A raw ticket
   object is dozens of fields of custom data, tags, and `via` metadata.
2. **`.slice(0, N)` every call.** 300 for a probe, ~1500 for a list. If a slice
   truncates, project harder — do not raise N.
3. **Never sideload.** `?include=users,groups` multiplies the payload. Fetch the
   one user by id instead.

## Endpoints

All relative, all GET, all `.json`.

| Endpoint | Project to |
|---|---|
| `users/me.json` | `{id, role}` — channel + auth proof |
| `views.json?per_page=100` | `{id,title}` — once per session |
| `views/{id}/tickets.json?per_page=25` | `{id,status,subject}` |
| `tickets/{id}.json` | `{id,status,priority,subject,requester_id,tags,updated_at}` |
| `tickets/{id}/comments.json` | count first, then `slice(-3)` |
| `search.json?query=…` | when you have no id |
| `users/{id}.json` | resolve one `requester_id` to a name |

A worked example — the last three comments on a ticket:

    (function(){
      var x = new XMLHttpRequest();
      x.open('GET', '/api/v2/tickets/12345/comments.json', false);
      x.send(null);
      var d = JSON.parse(x.responseText);
      return JSON.stringify({
        url: location.href,
        n: d.comments.length,
        recent: d.comments.slice(-3).map(function(c){ return {
          id: c.id, public: c.public, author: c.author_id,
          body: (c.plain_body||'').slice(0,800) }; })
      }).slice(0, 4000);
    })()

- **`plain_body`**, not `body` or `html_body`.
- **`public:false` marks internal notes** — prior troubleshooting lives there.
  Keep the flag in every comment projection.
- `per_page` caps at 100.
- **View order is not screen order.** If the human has sorted or filtered the
  UI, the top rows differ. Say which order you used.
- **`429` → back off and obey `Retry-After`.** The quota is shared with the
  human working alongside you. It does not mean try another channel.

## Where the API stops

- **Zendesk Explore** — no public API. GUI only.
- **Unsaved UI state** — what is typed in a composer, an open macro preview.
- **Attachments** are binary. Never pull the bytes into context — see below.
- **Anything a human is meant to look at** — navigate and let them see it.

## Attachments — screenshots are often the whole ticket

A customer's screenshot of an error dialog is frequently the entire content of a
ticket, so reading them matters. But **image bytes must never enter your
context**: a 500 KB screenshot is ~700 KB of base64, and context here is
append-only — you cannot prune it back out. One inlined image ends the session.

The comments endpoint lists attachments. Project only the metadata:

    d.comments.flatMap(function(c){ return (c.attachments||[]).map(
      function(a){ return {id:a.id, name:a.file_name, size:a.size,
                           type:a.content_type, url:a.content_url}; }); })

Then, for an image you actually need to read:

1. Get the file onto disk. Try the `content_url` directly first — it may be
   fetchable. If it returns HTML or 401 it needs the session: download it
   **inside the authenticated browser** so it lands in `~/Downloads`. Do not
   attach cookies to an external HTTP client; bot-shaped requests trip
   Cloudflare on this tenant (browser-ops).
2. Describe it out of band:

       scripts/describe-image.sh <path> ["specific question about it"]

3. **Append only the returned description.** A few hundred tokens of text
   replaces hundreds of kilobytes of image.

The description comes from a separate vision model on its own server
(`scripts/serve-vlm.sh`, port 8081). The agent server is deliberately text-only
— loading a vision projector there disables slot persistence, context shift and
cache reuse for *every* conversation, which is what produces the compaction
death spiral. See `config/llama-server.md`.

Ask a specific question when you have one ("what is the exact error text?")
rather than accepting a generic description. Non-image attachments — PDFs,
logs, CSVs — are not this script's job; read them as text.

## Composing with navigation

Ids from JSON → content from JSON. For a read-only question you are done, with
no navigation at all.

Navigate only to show a human something or to draft a reply: set the address bar
to `https://<host>/agent/tickets/{id}` and press Enter. Read the address bar's
element index fresh each time (browser-ops). This skips the ticket list
entirely, so neither AX index drift nor pixel drift applies.

## Writes — GET only

A CSRF token is available (`authenticity_token` from `users/me.json`) and write
endpoints exist. **Do not use them.** The standing rule is draft, never send:
compose replies and leave them for human review. Status changes, comments,
macros and assignments all require explicit per-action human approval, whatever
the mechanism.

## When a read comes back empty

An empty result is a channel failure until proven otherwise. Prove it with
something that cannot legitimately be empty:

    JSON.stringify({url:location.href, title:document.title,
                    ready:document.readyState, ok:1+1})

- nothing returned → JS execution is blocked; check the prerequisites above
- `url` is `about:blank` or not the agent tab → stale `window_id`; refresh it
- `ok:2` but your API call is empty → **you used a promise.** `fetch`, `await`
  and `.then()` all return empty here. Rewrite as synchronous XHR.
- the call broke rather than returned → check you did not pass
  `target_url_contains`

Never build a theory on an empty result.
